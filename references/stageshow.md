## Select only for a product illustration

Use for an explicitly requested or reference-locked hero/feature product illustration, bento product scene, still product shot, or short scripted UI walkthrough with a simulated cursor. It does not own full landing design, copy strategy, real application behavior, generic text reveals, real browser automation, or end-to-end product testing. Do not force it onto a text-only landing, a small bugfix, a real dashboard or a native desktop application.

Hallmark owns the visual research/reference lock, the approved brand owns tokens, Elaya owns the landing conversion argument; Stageshow implements the selected illustration inside that one shared brief and build. A scene is optional: choose it only when it demonstrates a verified product capability or is explicitly identified as concept/demo. Keep existing Hallmark/Unslop QA and the assigned website/video renderer. Never silently switch a HyperFrames-owned video to a competing renderer; port the scene choreography through that owner when needed.

## Consuming the module

1. Establish the slot, actual displayed desktop/mobile size, still vs loop, target product identity, story/action/payoff and allowed assets. Read the upstream workflow and relevant framing/craft/motion/kit/rehearsal references in full. Start from the closest licensed example, then adapt it to the actual brand and product, not the example's identity.
2. Keep the pinned submodule checkout unchanged: upstream recipes that create `examples/<yours>` must be adapted into the authorized project or task-owned preview, never written into the vendor tree. Read `package.json`, lockfile and scripts before executing them. Node >=20.19 is declared upstream; dependencies belong in the assigned application or an explicit task-owned preview, not globally in Hermes. Copy only required kit/example files and preserve license notices. Repository installation alone does not execute npm scripts, provision services or authorize any project upload.
3. `Act.click`/`Act.set` simulate a story; they do not click a real application or prove backend behavior. Label synthetic scenarios/data as DEMO or concept wherever they could be confused with live product output. Never invent proof, customers, financial outcomes or unsupported shipped features. A scenario can illustrate only verified functionality unless explicitly presented as a concept.
4. Preserve approved font/color/media roles over module defaults. MIT covers Stageshow source, **not every app icon or trademark**. Read `NOTICE.md`, `assets/app-icons.ts`, `kit/brands/SOURCES.md` and applicable per-asset licenses before reuse; use owned/permitted product assets, not another product's identity.
5. For a real scene deliver editable source and the requested still/interactive/export artifact. Exercise desktop and compact mobile layout, static poster/reduced motion, action targets, full sequence and loop seam. Check clipping, readability and the focal payoff. Use deterministic capture and its gate where supported, then visually inspect actual rendered output; a passing capture gate alone is not sufficient. Exports/publication remain task-scoped effects.
6. Report separately: source module installed; dependencies/build exercised; scene rendered; output visually reviewed; published. Do not claim unexercised stages. This installation does not itself produce a product demo.

## Routing checks

Positive: «сделай продуктовую сцену в hero» -> shared design brief + this module. «Покажи в bento, как работает импорт» -> verified capability + scoped Stageshow scene. «Демо с курсором» -> simulated walkthrough, not real automation.
Negative: «проверь, реально ли работает оплата» -> real product E2E, no Stageshow substitution. «Исправь CTA» -> functional repair, no illustration. «Нативное desktop-приложение» -> existing desktop route. «Анимируй заголовок» -> existing text/motion route unless a product scene is actually requested.
